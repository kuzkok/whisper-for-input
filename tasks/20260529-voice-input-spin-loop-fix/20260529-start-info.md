# Фикс spin-loop в voice-input при отвале evdev-устройства

Дата: 2026-05-29
Статус: запланировано

## Контекст

«Отложено»). Реструктуризация репо уже выполнена и слита в master, поэтому

кладём в `voice-input/tests/`.

## Симптом

При отключении evdev-устройства (Microsoft 2.4GHz receiver и подобные
USB-приёмники, уходящие в сон / выдёргиваемые) демон `voice-input` уходит
в tight loop и жжёт 100% CPU на одном ядре.

## Диагноз

Цикл событий в `voice-input.py:listen()` (`voice-input/voice-input.py:81`):

```python
selector = selectors_module.DefaultSelector()
for dev in devices:
    selector.register(dev, selectors_module.EVENT_READ)

while True:
    for key, _ in selector.select():        # :94
        dev = key.fileobj
        try:
            for event in dev.read():        # :97
                ...
        except OSError:                      # :145
            pass                             # :146  ← глушит, но fd не снимается
```

Когда устройство отваливается, его fd становится «мёртвым»: `selector.select()`
постоянно возвращает его как готовый к чтению, `dev.read()` бросает `OSError`,
который молча гасится `except OSError: pass`. fd **не дерегистрируется** из
селектора → `select()` немедленно отдаёт его снова → бесконечный busy-loop без
блокировки. CPU 100%.

## Предлагаемый фикс

- На `OSError` от `dev.read()` — **дерегистрировать** fd (`selector.unregister(dev)`)
  и закрыть устройство (`dev.close()`), а не просто `pass`. Назовём это `drop()`.
- Если после `drop()` в селекторе не осталось устройств — корректно завершиться
  или ждать переподключения (см. ниже), а не крутить пустой `select()`.
- **Hotplug**: добавить `DeviceWatcher` с периодическим `discover()` — rescan
  `/dev/input/event*` по тем же критериям отбора (имя/`KEY_*`-capabilities,
  что и при старте), чтобы переподключённое устройство снова регистрировалось
  без перезапуска сервиса. Период — например, раз в N секунд через таймаут
  `select(timeout=...)`, чтобы не плодить отдельный поток без нужды.

## Тесты

`voice-input/tests/` (создать). Нужны fake-устройства, без реального evdev:

- Fake `InputDevice` с управляемым `read()`, который умеет бросить `OSError`.
- Тест: после `OSError` устройство дерегистрируется из селектора и больше не
  опрашивается (нет busy-loop) — например, проверкой, что `select` не зовётся
  в плотном цикле / счётчик вызовов ограничен.
- Тест: `discover()` подхватывает «переподключённое» устройство и регистрирует
  его заново.
- Тест: при потере всех устройств демон не крутит CPU (ждёт/таймаутит).

Прогон: `cd voice-input && python -m pytest` (либо из корня с указанием пути).
Зависимости лёгкие (`evdev`, `pytest`) — отдельный venv серверного стека не
нужен; см. CLAUDE.md, раздел про потребителей.

## Проверки после фикса

1. Юнит-тесты с fake-устройствами зелёные.
2. Ручная проверка: запустить демон, физически выдернуть/усыпить USB-приёмник —
   CPU не уходит в 100%, в логах видно `drop`; воткнуть обратно — устройство
   снова работает (hotplug через `discover()`).
3. `systemctl --user restart voice-input` и проверка `journalctl --user -fu voice-input`.
